# development-time

Measures where development time actually goes when working with Claude Code, from the
session transcripts Claude Code already writes plus the git history of the affected
repositories. Produces an interactive HTML report.

The headline question this answers: **how much of the time is building the feature, and how
much is tests, documentation and everything else?**

## Result on the measured sample

59 calendar days, 556 sessions, 31 projects, 530 hours of attributed time:

| Activity | Hours | Share of active work |
|---|---:|---:|
| Tests (writing + running) | 124 | 27.3% |
| Verification (build, lint, running the app) | 85 | 18.7% |
| Git and infrastructure | 80 | 17.7% |
| Code exploration | 69 | 15.2% |
| **Feature code** | **51** | **11.2%** |
| Docs and planning | 45 | 9.9% |

The initial hypothesis — feature work at 25%, tests taking the rest — was directionally
right but understated: feature authoring is **11.2%**, less than half the expected share.

The strongest finding is the maturity relationship:

```
test share of time = -20.0 + 0.748 × maturity      R² = 0.79  (n = 14)
feature share      =  20.6 - 0.150 × maturity      R² = 0.72  (n = 14)
```

A greenfield project spends near 0% of its time on tests; a mature one around 36%. This is
measured, not assumed.

## Pipeline

One command does everything:

```
build.cmd            full run
build.cmd fast       reuse the existing repository scan (skips the slow step)
build.cmd page       rebuild only the public HTML from existing data
build.cmd local      build the internal copy instead (names every client)
```

It runs the six steps below, renders the **public** page to `docs/index.html`, and then
refuses to finish if that page still contains anything private.

```bash
python analyze.py        # transcripts    -> data.json
python repo_metrics.py   # working trees  -> repos.json        (slow: walks every repo)
python git_delta.py      # git history    -> git_delta.json
python before_after.py   # git history    -> before_after.json
python model.py          # joins + fits   -> report_data.json
python build_report.py   # -> report.html (private, full detail)
python verify_public.py  # blocks the build if the public page leaks
```

No third-party dependencies — standard library only. Needs `git` on PATH.

### The two builds

| Build | File | Contents |
|---|---|---|
| Public | `docs/index.html` | Client projects appear as `Client project N`. Committed. |
| Internal | `report.html` | Every project named. Git-ignored, never committed. |

Both carry identical measurements — the redaction changes names, not numbers. Build the
internal copy with `build.cmd local` (or `python build_report.py --out report.html`)
whenever the full detail is needed for an internal audience; delete it freely, it
regenerates in seconds.

## Publishing to GitHub Pages

The report is built locally and only the finished page is committed. Nothing in the
repository needs to be regenerated by CI, and no measurement data is published.

**What gets committed**

```
docs/index.html      the report — one self-contained file, no external requests
docs/.nojekyll       tells Pages to serve it verbatim
*.py, build.cmd      the pipeline, so the methodology is auditable
README.md
```

**What must never be committed** — `.gitignore` already covers all of it:

`data.json`, `repos.json`, `git_delta.json`, `before_after.json`, `report_data.json`
and `report.html`. Every one embeds absolute local paths (`D:\Git\...`) and client
project names.

**Why redaction is needed at all.** The page carries its dataset inline, so filtering a
table only hides rows from view — the underlying records are still in the HTML source.
`build_report.py --public` therefore rewrites the data before embedding it: it drops every
`cwd`, and renames projects outside `alegauss` and `viglet` to `Client project N`. All
numbers are left untouched, so totals, shares and fits remain exactly as measured; only
identities are withheld. `verify_public.py` then re-reads the *private* dataset, derives
every string that must not appear, and greps the built page for each one — so the check
fails if the redaction ever silently stops covering a new field.

To widen or narrow what may be named, edit `PUBLIC_OWNERS` in `build_report.py` and
`LISTED_OWNERS` in the report script.

**One-time repository setup**

1. Create the repository and push.
2. Settings → Pages → Source: **Deploy from a branch**, Branch: `main`, Folder: `/docs`.
3. The page appears at `https://<user>.github.io/<repo>/` within a minute.

No Actions workflow is required. For a custom domain, add `docs/CNAME`. To keep the page
out of search results, add `<meta name="robots" content="noindex">` to `META` in
`build_report.py`.

**Routine**

```
build.cmd
run-commit.cmd -m "docs: refresh development-time report"
git push
```

## What each step does

**`analyze.py`** rebuilds every session as a chronological event stream and attributes the
interval between consecutive events to the activity in progress. Emits per-project,
per-month and per-session buckets, plus an audit trail of the time it deliberately did not
count.

**`classify.py`** holds every heuristic: which paths are tests, which shell commands are
test runners vs builds vs running the app, which tools are planning overhead. Tune the
rules here; nothing else needs to change.

**`repo_metrics.py`** walks each repository to count source/test/docs lines and asks git
how old the history is, then computes the maturity index.

**`git_delta.py`** measures delivered lines two ways: the sum of per-commit additions
(churn) and an end-to-end diff from the last commit before the first session to HEAD
(delivery). The report uses the second.

**`before_after.py`** attempts the natural experiment — same repo, same author, equal
windows before and after adoption. **It does not produce a usable result** on this dataset;
see Limitations. It is kept because the failed attempt is part of the methodology.

**`model.py`** joins the three sources, fits the maturity relationships, and writes a
compact dataset for the report.

**`build_report.py`** renders the HTML. All adjustable assumptions are computed in the
browser so the reader can change them and watch the numbers move.

## Time attribution rules

| Rule | Value | Why |
|---|---:|---|
| Max per work interval | 4 min | Longer means the developer stepped away mid-turn |
| Max per test run / build | 15 min | These legitimately block for minutes |
| Max per human pause | 20 min | Longer is a break, not review time |
| Gap that ends a work block | 45 min | Discarded whole |

Every cap **reduces** the measured total. On this sample, 1,339 hours of raw session span
reconciles exactly to 452 h active + 78 h interaction + 38 h trimmed by caps + 771 h of
breaks. The bias is toward understating time, never inflating it.

## The two counterfactual models

How long the same work would have taken without Claude Code cannot be measured, only
modelled. The report presents two models rather than one number, because they answer
different questions:

**Model A — per-activity multipliers.** For each measured activity, how many times longer a
developer would take doing the same thing by hand. Assumes the same work and the same
decisions. Lands at **≈3.1×** on default multipliers. This is the figure to use for
planning.

**Model B — delivered lines at a human authoring rate.** Applies lines-per-hour rates to
the lines that actually landed in git. Assumes the entire delivered scope would have been
hand-written. Lands at **≈55×**.

The gap between them is the cost of one assumption: that scope is constant. It is not —
190,750 lines of tests and 36,627 lines of documentation are exactly the work that gets
trimmed first when a human writes every line. Model B is best read as a ceiling: what the
delivered artefact would have cost if every line of it had been mandatory.

Both models' parameters are sliders in the report. Neither is a measurement, and the report
labels them as assumptions throughout.

## Limitations

- **Lines of code measure volume, not difficulty.** Model A exists so the primary
  comparison does not depend on line counts at all.
- **No reliable before/after.** Several repositories are git worktrees of the same
  codebase, so an earlier worktree's sessions fall inside the supposed "before" window; in
  others a single bulk import dominates the diff. Per-active-day ratios came out between
  0.0× and 4.3× with no interpretable pattern.
- **Git cannot separate assisted from manual commits here.** Commits are authored solely by
  the developer by process choice, so the co-authorship trailer is absent from most of the
  history and would produce false negatives.
- **Manual testing is a floor, not a total.** Only pauses whose next message showed evidence
  of hands-on testing are counted. See instrumentation below to fix this going forward.
- **One developer, one set of projects.** Nothing generalises without fresh measurement.

## Measuring manual test time properly, from here on

Retrospective analysis cannot see testing done after a session ends. `hooks/` contains a
`Stop` hook that stamps the end of each work cycle and a `UserPromptSubmit` hook that stamps
the resumption, writing both to a local JSONL log. With those installed, the gap is measured
directly instead of inferred.

Install per project (or globally in `~/.claude/settings.json`):

```jsonc
{
  "hooks": {
    "Stop": [
      { "hooks": [{ "type": "command",
                    "command": "python /path/to/hooks/cycle_stamp.py stop" }] }
    ],
    "UserPromptSubmit": [
      { "hooks": [{ "type": "command",
                    "command": "python /path/to/hooks/cycle_stamp.py resume" }] }
    ]
  }
}
```

The log lands in `~/.claude/dev-time-cycles.jsonl`. Once it has data, `analyze.py` will
prefer measured turnaround over the inferred floor.

## Reproducing a single number

Any figure in the report can be traced. For example, the delivered-lines count for one
repository:

```bash
git -C <repo> rev-list -1 --before=<first-session-date> HEAD   # the base commit
git -C <repo> diff --numstat <base>..HEAD                      # additions/deletions per file
```

And the per-activity totals are decomposed in the report's evidence table as
*operations × average duration*, so each row is independently checkable.
